# 1. 研究の目的と実験の識別

## この研究が解く問題

燃料バスと併用する営業所で、電気バスへどの便を担当させ、運行の合間と帰庫後にどう充電すれば次の運行も成立させられるかを計画し、その運用費を評価する。時刻表そのものを変更したり、電気バスだけに全便を強制したりする研究ではない。

当面の成果は、平日・土休日を含む連続7日間の運行・充電、週次費用、各月代表週での違いである。最適化はそれを得る方法。全ケースの厳密最適性を証明し終えるまで、検算済み候補の集計・図表を止めない。一方、未担当便、日境界の不整合、SOC・電力収支・会計の誤りは放置しない。

PV・BESS・日射条件は運用の入力・設備条件。題目の主研究を太陽光の時間変動や受電電力へ置き換えない。将来の導入採算・補助額は、運用費評価を土台に別途必要な費用と比較を加える段階である。

題目の相談候補と先生への説明は[2026-10-06のSlack対応](../../../outcome/2026-10-06_slack_title_review/RESEARCH_TITLE_AND_REPLY.md)。第一候補は「燃料バスと併用する電気バスの便割当・充電計画の最適化」。先生未承認。混成運用や多日SOC管理は先行研究にもあり、それだけを新規性としない。

## 日をまたぐとは何をすることか

- 車両ごとのSOC、所在、運行・回送、充電接続状態とBESS残量を次の区間へ継承する。
- その日の日付・ダイヤ・PVと料金系列を使用する。曜日を7回反復した結果にしない。
- 計画窓が重複しても、実際に採用した区間だけを会計へ計上する。
- 翌朝SOC目標は、営業便の時刻だけでなく、その前の出庫回送と充電可能な完全区間を考慮する。回送後にも満充電を要求する誤った期限へ戻さない。
- 最終翌朝を含むかは設定事項。今回の主実験は含む。別条件なら新しい版として区別する。

週の内部をSOC等の継承なしに日別ジョブへ分け、7本の費用を足したものは連続週ではない。別PCへの並列化単位は独立した代表週×シナリオである。

## 何を完了と言うか

| 判断 | 意味 |
|---|---|
| 設定保存・期間登録 | 求解開始ではない |
| Prepared作成 | 入力を凍結した。投入・求解済みではない |
| QUEUED | RAM・端末・ライセンス等を待つ |
| プロセスCOMPLETED | 計算プロセスが終了した |
| 物理・会計確認 | その範囲の検査に通った。元の判定と検査範囲を保存する |
| 条件付き週次評価 | 保存済み検算結果を用い、前提付きで運用費を記述比較する |
| 正式研究採用 | AGENTS.mdの研究ゲートと独立レビュー等を満たした。上の状態だけで代替しない |
| 最適性 | 対応する同じ問題・目的関数の有効な下界とgap等で示す。週全体は未証明 |

今回のdriver要求は `research_run=false` の条件付き評価用である。これを正式研究実行済みへ書き換えない。研究採用保留の元結果は診断・不採用範囲を保持し、条件付き記述評価とは別に示す。

## 改修と実験の優先順位

1. 使える原結果を確認し、再集計・図表で成果にする。
2. 不足・失敗の影響範囲だけ修正する。他の成立済み週を止めない。
3. 計算・検算・会計を妨げる箇所へ最小の変更を加える。
4. 実行コード・物理条件を変えた再実験は新しいclean固定版・Prepare・attempt・出力先にする。旧結果を新SHAの成果にしない。
5. 改善量が必要な組だけ、同一条件で実行可能な参照案や追加予算を検討する。

厳密解法の証明、PC台数拡張、全体再設計を、現在の12週の成果取得より先の主目的にしない。追加費用、契約、資格情報・OS設定、Slack/メール送信は、その時点の依頼と許可の範囲を別に確認する。
