# 2. 入力・パラメータと版の扱い

## 四つの保管単位を分ける

| 単位 | 役割 | 変更方法 |
|---|---|---|
| ODPT/Solcast等の取得原本 | 出典、取得日時、要求、hashを残す | 研究者が明示的に取得・更新する。ジョブごとに取得しない |
| 最適化用snapshot/DB | 検証済みデータを読取専用で使う | 手動の検証・凍結。変更時は新しい実験版 |
| 親シナリオと期間別計画 | 共通の路線・車両・設備と、開始日・日数を管理 | フロントで保存。実行済み期間は勝手に変更しない |
| Prepared・実行manifest | そのrunが使う入力と実効条件を凍結 | 正規Prepareから作成。workerで再生成しない |

時刻表の取得・監査・DB生成は手動作業で、通常のPrepare・ジョブ投入・求解へ追加しない。今回の取得原本がないからとODPTへ自動再取得してはいけない。別時点のデータを同じ比較へ混ぜない。

## 今回の入力DB

実際に使った場所は配置済みreleaseの下の
`C:/master-course/output/cluster-deployment/release-executed-soc-20260926/data/optimization/shibu21_23_frozen_20260924/`。

- `source.sqlite3` の記録hash：`70b99fca42d70a408d39f1b00e9768ce51b71f4cbfec1eb8e794c06d52738286`。
- テーブル：`selected_routes` 16行、`timetable_rows` 648行、`stop_sequences` 16,586行、`stops` 77行。
- 648行は元のカレンダー別データで、週全体の便数ではない。今回の12週は各1,704便。各日の展開後の便IDをPreparedで確認する。
- 距離は停留所列のHaversine折線による代理距離。実道路距離と同じとはしない。入力状態は `DIAGNOSTIC_SOURCE_CAPTURE_VALIDATED_DISTANCE_PROXY_DECLARED`。

開発rootには同じDBがないことを2026-10-06に確認した。旧実験の操作はsettingsが指定する固定releaseで行う。新しいreleaseに必要なsnapshotが欠けている場合は投入を止め、照合済み原本から明示的に配置する。ダウンロード・DB再生成・guard削除による自動補完はしない。

既存Go取得器は `scripts/catalog/capture_tokyu_company.go`、手動snapshot処理は `scripts/catalog/manual_tokyu_company_snapshot.py`。新取得を依頼された時だけ使用版の引数を確認する。本資料作成では実行していない。トークンは環境/安全な資格情報保管から読み、文書やmanifestへ値を書かない。

## 今回の主要値

下表は今回の固定入力の説明であり、将来シナリオに強制する既定値ではない。確認元は2月Preparedと[12週／旧1日条件の照合記録](../../notes/DAY_WEEK_PARAMETER_COMPARISON_20260927.md)。各実験の原本と実効設定を優先する。

| 項目 | 今回の条件 | 注意 |
|---|---|---|
| BEV | 35台、314 kWh、1.316 kWh/km、車両充電90 kW、SOC20〜90% | 初期SOCは車両別。全車を80%へリセットしない |
| ICE | 25台、燃費4.52 km/L、タンク160 L | 実燃料Lを費用調整のため変えない |
| 充電器 | 10基×90 kW | 接続・占有・車両適合も検査する |
| PV | 1,000 kW、15分系列 | 総発電入力、非走行営業所負荷0という仮定。過去の余剰PV入力と別 |
| BESS | 6,000 kWh、900 kW、初期3,000 kWh、1,200〜4,800 kWh、効率各0.95 | BEVの20〜90%と混同しない |
| 買電・燃料 | 30円/kWh、軽油150円/L | 期間・実効系列・モデル係数を会計と照合する |
| 車両使用費 | 20,000円/使用車両日 | 車両購入費ではない。単位と日数を併記 |
| CO₂ | 価格1円/kg | 係数の出典・日付と実行会計を保持。図表だけの警告と本体会計不整合を分ける |
| 契約基準 | 200 kW、超過電力量のモデル費用500円/kWh | 実設備の物理上限や現実の料金制度の証明ではない |
| 折返し・回送 | 基本折返し10分、回送速度18 km/h | 実効接続条件はPreparedの遷移・原距離も確認する |

汎用設定の `initial_soc=0.8` があっても、実車両別Preparedの `initialSoc` を優先する。2月の先頭BEVには0.248771という値がある。全台のSOCを一つの既定値で上書きしない。

費用の単一フラグだけで「未計上」と決めない。今回 `enable_vehicle_cost=false` でも `cost_component_flags.vehicle_usage_cost=true` で車両日費が計上される。購入費と使用費を分け、最終実行会計の実効費目を確認する。0、未設定、無効、対象外、欠測はそれぞれ区別する。

機械的な確認先は[2月Preparedの主要値抜粋](parameter_map_20261006.json)。原ファイルの階層と値を対応させる。PVは `pv_capacity_input_mode=rated_output_manual`、手動容量の仮定であり、営業所面積や実設置可能量の承認ではない。genericタンク容量等より実車両別値を優先する。

抜粋JSONの値はPrepared内の宣言値で、最終会計の実効係数を全て認証したものではない。特に `depot_power_limit_kw=200` というキー名だけから物理hard limitと判断せず、超過方策と会計を追う。CO₂係数も原会計・元データと照合する。充電は `piecewise_soc_taper_v1`、接続準備・解除各5分、最小session15分の宣言があり、常に全車が90 kWで充電するとはしない。

## BEVの翌朝SOCと末尾

合意した目標は運用上限SOC。今回は90%で、最低SOCは20%。帰庫後から翌朝出庫前の窓で充電する。営業便の出発前に出庫回送がある場合は、その前に充電を完了する契約を適用する。

`bev_soc_deadline_mode=next_morning_operational_max`、`final_overnight_mode=include`、`final_soc_target_percent=90`。1週は672個の15分区間だが、今回の集計は末尾を含め695または697区間。追加長は `prepared.json` の `overnight.extra_slots` で確認し、全週23区間と決め打ちしない。

末尾を除外する設定は別の比較条件になる。未達を成功にするため範囲を黙って672へ縮めない。翌朝の目標を達成したことと、目標達成の余裕が十分あることも別。上限と等しい目標では目標との差は余裕指標にならない。

## BESSの合意済み方策

バス充電へ供給したPVの余剰でBESSを充電し、残量が下限なら待機、上限なら余剰PVを抑制する。系統からBESSへの充電は不可。追加の初期在庫保護と終端初期値への復元は課さない。

入力では設備の `bess_priority_mode=pv_self_consumption`、終端 `minimum_only`、毎時終端 `minimum_only`、予備 `physical_floor_only` を確認する。方策が設備配列内にある場合、上位設定に同名キーがないことだけで未設定と判断しない。

初期3,000→終端最低1,200 kWhという有限期間の在庫利用を、当該週のPV発電や恒常的節約に数えない。初終端と損失を明記する。先生から長期評価が求められた時は別実験条件として設計し、合意済み本体へ終端復元を勝手に戻さない。

## 気象とカレンダー

2026年時刻表を2025年気象条件で評価する仮想運用実験。2025年の実運行を再現したとはしない。計画用は学習年のみのclimatology proxy、実行時の評価系列と区別する。実時点のSolcast予報性能を検証したとはしない。

電費・燃費は今回固定で、気温/HVACの季節消費を全面評価していない。主に日付別ダイヤとPV条件が変わる比較として説明する。2025年の晴れ・くもり・雨の標準カーブは記述統計で、予測モデルの訓練と混ぜない。

旧入力の説明文字列に晴雨対照由来の語が残ることがある。`service_dates`、`date_series_contract`、実PV方策・出典、Prepared hashで実験を判定する。実行途中に説明文字列まで書き換えない。

## 求解要求と実効設定

| 要求 | 今回の宣言 |
|---|---|
| profile / mode | `existing_solver_v1` / `mode_milp_only` |
| 運用 | `day_ahead_and_hourly_rolling`、採用区間60分 |
| seed / threads | 42 / 4 |
| 時間 | 共有要求7,200秒、Stage 1 1,800秒、Stage 2 600秒 |
| gap | 各求解の1%目標。達成してもStage 1／固定配車Stage 2／毎時窓の品質であり、週統合最適性は示さない |
| Stage 1探索 | `bounded_presolve_dual`、遅延制約、疎な充電窓、営業所接続の因子化 |
| repair / fallback | 正式条件では禁止。今回の後処理修復もfalse |

要求値は実効値ではない。機器ごとのRAM予算、毎時窓の有効時間/数値設定、停止理由はnative log、solver metadata、実効controlsで確認する。7,200秒を「週全体が必ず2時間で終わる」と解釈しない。Stage 1の目的と下界、固定配車Stage 2の目的、最終実行費用は別。

## 新条件にする前に書く差分

変えるキー、元値、新値、理由、数理条件/可行域/費用/比較可能性への影響を記録する。変更しないキーと原本hashも残す。親シナリオとPrepared、コード、環境、出力先を同じ実験版に束ねる。

特に台数・SOC、BESS方策、便/回送/距離、受電上限、費用係数、PV境界、時間刻み、遷移削減は、成功させるために黙って変更しない。変更案は別条件として検査し、旧結果をその成果へ流用しない。
