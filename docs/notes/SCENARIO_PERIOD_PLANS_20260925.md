# ひとつのシナリオで複数期間を管理する

共通の路線・車両・設備はシナリオに置き、日付と日数は「期間別計画」へ登録する。
各月の代表週を別シナリオとして一覧へ増やさない。実行時のPrepared snapshotは
再現性のため別に保持し、親シナリオ・期間・attemptを対応付ける。

今回の「仮・正式用」は `771d115b-75b0-49f7-a7f0-25f259a2cd21`。
2025年1～12月の既存代表週12件を登録し、既存2キャンペーンへひも付けた。
週選定、凍結された親入力、投入済みjob、求解コードは変更していない。
四季は表示上の集約であり、実験単位は各月の連続7日間である。

## 操作

シナリオを選び「期間別計画」で開始日・日数・名前を追加して保存する。
保存は計算の開始ではない。実行済み期間の日付変更・削除は拒否し、新しい期間を追加する。
同時編集はrevisionで拒否する。入力準備と検算を別々の割合で表示し、実行先、job ID、
固定SHA、待機理由、エラー、取得日時は実行記録を開いて確認する。
120秒以上古い監視、通信断、読取不能は状態不明と表示し、完了と誤認しない。

計画はシナリオstoreの隣の `scenario_periods.sqlite3` に保存される。
同じシナリオの運用情報であり、最適化入力hashには混入させない。
バックアップ時はこのDBも含める。ローカルCLIだけがcampaignの実パスを登録でき、
HTTPから任意のローカルファイルを参照することはできない。

```powershell
$env:SCENARIO_STORE_PATH = 'C:\master-course\output\scenarios'
python tools/research/scenario_periods.py show --scenario 771d115b-75b0-49f7-a7f0-25f259a2cd21
python tools/research/scenario_periods.py export --scenario 771d115b-75b0-49f7-a7f0-25f259a2cd21 --output output/period-plan-new.json
```

出力済みplanは上書きしない。固定した新実験版で既存の `weekly_campaign.py run`
に `--period-plan output/period-plan-new.json` を渡すと、親IDと週一覧を使用する。
`--settings` と `--output` は引き続き必要。clean SHA、DB、親hash、資源・ライセンス、
Prepare、物理・会計契約は既存の経路で検査する。実行manifestはシナリオIDのhashを含み、
同じSHA・同じ週を別シナリオで実行しても冪等キーが衝突しない。

登録可能期間は1～366日だが、この週次driverは7日間に限定する。他の日数の計画を
7日へ黙って変換しない。連続数週間の求解対応を、この登録機能だけで保証しない。
今回の12週は独立代表週であり、52週の連続運用ではない。

## 5月の停止原因と修正範囲

固定0964b783の5月attempt `a0679a14-3f67-5cc1-bbbd-bbc5475c32ff` 原本を確認。
IISは車両35f95479のslot600における回送中充電禁止、充電電力、翌朝SOCの3制約。
運用上限を営業便開始前の共通時刻で要求したため、その前に出庫回送した車両が
走行消費後にも上限を要求されていた。固定配車の充電と独立SOC再計算の判定を、
既定期限と車両の翌朝出庫前の最後の完全区間のうち早い方へそろえた。
回送消費、SOC上限・下限、最終夜間の有料区間は維持する。

そのStage2不可行性を受けた配車再探索では、seed証拠の排他的作成が既存ファイルに
衝突しFileExistsErrorとなった。初回seedは保持し、feedback iterationごとに別名で
保存する。同じiterationの二重書込は引き続き拒否する。

これは数理的なSOC判定時刻に影響する。旧結果の成功化・再ラベルはしない。
Stage1は充電の緩和問題であり、固定配車下Stage2と週次物理検算を省略できない。
稼働版へhot patchせず、新しいclean実行版の再検証が必要。

本番研究の承認は独立レビュー・新版の実規模7日完走後に判断する。
単体テスト、画面表示、原本の原因特定だけで「本番用に問題なし」と宣言しない。
