# BESSを補助設備として扱う運用（2026-09-21）

ユーザーの最新指定は「BESSは本題ではない。SOC範囲内で使えれば使い、使えなければ待機。
PVはバス充電を優先し、余りでBESSを充電する」。この方針を計画・実行に反映した。
追加予備・終端復元は設けない。BESS範囲比較を次の主要課題にせず、配車・バス充電の改善へ集中する。

## 運用ルール

1. その時刻のPVを、予定したバス充電に先に使用する。
2. バス充電の不足分に、下限までの使用可能残量と出力上限の範囲でBESSを使用する。
3. BESSが下限なら放電0。足りない分は既存の買電条件で補い、バスの充電要求は変えない。
4. PVがバス充電より多ければ、その余剰だけを上限・充電出力までBESSへ充電する。
5. BESSが上限なら充電0、残ったPVは抑制する。次に余剰が出れば下限で待機したBESSも再充電できる。

既定は20–80%。既存の明示された10–90%感度分析にも同じルールを適用できる。
SOC上下限で指令を飽和させるため、残量不足の放電指令や満杯への充電指令を固定して運行全体を止めない。
PV→バスとBESS放電で同じ需要を二重充足せず、BESSの同時充放電は生じない。
買電の出力制限・超過費、バスSOC、運行時刻・帰庫、エネルギー保存と効率は従来の条件で評価する。
観測SOC自体が範囲外・非有限などの入力異常は、残量を書き換えて正常扱いにしない。

## 数式と意味

各slotのバス充電要求をD、PVをP、開始在庫をE、出力上限×時間をQとする（いずれもkWh）。
充電効率ηc、放電効率ηd、使用下限L・上限Uに対し、

```
PV→バス      = min(P, D)
BESS→バス    = min(D − PV→バス, Q, (E − L) × ηd)
PV→BESS      = min(P − PV→バス, Q, (U − E) / ηc)
系統→バス    = D − PV→バス − BESS→バス
PV抑制       = P − PV→バス − PV→BESS
次の在庫     = E + ηc × PV→BESS − BESS→バス / ηd
系統→BESS    = 0
```

許可されていないBESS方向は0。無効設備も0。L/Uに達すれば該当する充放電が0になる。
例えばL=20、E=20、D=12、P=3なら、PV3・買電9・BESS0。
次にD=10、P=30なら余剰20を充電し、ηc=0.9でE=38へ回復する。
続いてD=30、P=0、ηd=0.8なら14.4を放電し、買電15.6・E=20となる。

これは運用方針を固定した総費用問題であり、BESSの時系列運転まで自由に選ぶ以前の問題とは異なる。
将来の高い電気料金のために残量を温存する等のBESS裁量を外したため、費用改善や計算高速化は保証しない。
単純で説明可能な補助制御の下で配車・バスの充電時刻を評価する。旧条件の結果を新方針の実測値に転用しない。

経路は design → seasonal Prepare → Prepared設備 → ProblemBuilder → Phase3固定配車Stage2 →
canonical flow → 実PV prefix制御 → 既存の実行会計。
Prepareでmodeを保存し、事前検査でmode脱落、追加予備・復元・系統からの蓄電との矛盾を検出する。
既定範囲・親の容量/初期残量/出力/効率は変更しない。

固定配車Stage2と既存の統合充電モデルには同じmin規則を求解前から組み込んだ。
[Gurobi MIN制約仕様](https://docs.gurobi.com/projects/optimizer/en/current/reference/python/model.html#Model.addGenConstrMin)を使用する。
求解後に都合のよいフローへ置換する後処理ではない。Stage1の連続エネルギー近似はこの規則を緩和したままで、
その事実をrecourse input metadataへ保存する。週間の統合Phase4対応・全体最適性は今回の変更で完了しない。

実行側は現時点のPV・BESS残量のみを使う。バス充電要求は固定し、BESSの以前の指令はこの宣言済み制御で更新する。
`pv_bus_first_surplus_storage_v1` をdepot別auditへ記録し、従来の固定BESS指令方式と区別する。
新方式には固定BESS指令のための追加prefix予備を課さない。硬い買電上限を持つ場合の予備検査は、
PV/BESSが使えなくてもバス需要を系統で賄える条件を確認する。超過を許す既存契約では実行超過費を記録する。
