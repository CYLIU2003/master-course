## WP0: 物理契約

到達経路は BFF最適化入口 → Prepare/materialization → `ProblemBuilder` →
`MILPOptimizer` / `GurobiMILPAdapter` → hourly Rolling → independent physical event
validation → executed accounting finalizer。旧Stage 2・統合経路ではSOC上限が
容量で、Prepared `maxSoc` がcanonical型へ渡っていなかった。

修正では、元の `minSoc/maxSoc` を容量と掛けてkWh化し、`maximum_soc_kwh` と
`soc_input_unit=kwh` を持たせる。Stage 1の充電余力、Stage 2と統合モデルの
すべてのSOC変数・最終遷移、Rolling入力検査で使用する。入力の不整合は拒否し、
残量の切り詰めや無料補給は行わない。独立イベント検証はPreparedの原レコードも
読み、canonical上限が欠落・改変していれば拒否する。未使用車両の初期状態も検査する。

数学的効果: `E[v,t] <= C[v]` を `E[v,t] <= C[v] * maxSoc[v]` へ変更する。
明示minSocとreserve/終端下限のうち厳しい値を維持する。充放電量や物理単位、
運行接続制約は金額の調整に使用しない。制約集合が変わるため旧計算値は再使用不可。

局所回帰では2段階・統合MILPの両方を実際のGurobiで確認した。
旧2ケースのクリーンな凍結コミットからの正式再実験・独立レビューは未完了。

BESSの `daily` は各日末に固定初期値へ戻す等式、`evaluation_period` は期間末の等式。
Rollingの窓末端条件は別の制約であり、同じ比較条件として記録する。

2日人工ケースをGurobiで解き、24時間窓・日次BESS境界を確認した。関連48件を通過。
夜間留置はユーザー回答により毎日弦巻へ帰庫と確定（最新追補参照）。既存経路の帰庫可能性だけからの夜間充電推定、
複数dutyの帰庫／出庫回送と連続SOC、ICE燃料、実行位置の統合は未完了。

曜日別の元便数と照合する。旧グローバルカタログの別版とは混在させない。週内の平日反復回数を
元ダイヤの便数へ加算しない。隣接リスト生成では全便ペアを判定したまま、通常の構築に不要な

## WP4: 評価用予報proxy

`config/seven_day_evaluation.json` で、2024年のみを学習、2025年2/5/8/11月と2026年2月の
最初の月曜から7日を評価週とする暦上の選定を固定した。最適化結果による週の選別はしていない。
低温降水2日を除く364日で12分類の時刻別減衰を学習し、未知の将来天候クラスは学習頻度で平均する。
太陽位置は[NOAA式](https://gml.noaa.gov/grad/solcalc/solareqns.PDF)、日射の基準形は
[Haurwitz式](https://pvlib-python.readthedocs.io/en/stable/_modules/pvlib/clearsky.html#haurwitz)を使用する。
幾何高度を使用し屈折補正なしの近似であることを記録し、対象日の実現気象を形状計算へ渡さない。
発行時刻・有効区間・lead time・学習終了日を出力し、学習情報が発行時点より未来なら拒否する。

`scripts/weather/build_forecast_holdouts.py` は学習モデル、5週の予報、実現推定値との比較CSV・誤差、
168回の発行予定と各ハッシュを `data/derived/seasonal_irradiance/tsurumaki/forecast_holdouts/` へ保存する。
同じ気候値を毎時再発行する基準で、更新による情報改善・Solcast予報精度は主張しない。
通常の予測関数に将来実現値や晴雨ラベルは入力しない。クラスを明示する別モードは
`known_class_oracle_reference` と表示する。

### 予測と実行の分離

Tk Prepareの「複数日のPV情報」で、`historical_perfect_information`（実測推定PVを事前既知とする参照）
と `training_only_forecast_proxy`（2024年学習の予測代理）を選択する。前者を実際の天気予報と呼ばない。
後者の予測関数にはモデル、対象時刻、発行時刻だけを渡す。別の実測CFファイルを内容ハッシュ付きで
保存し、canonical problemには将来実測値の配列を載せない。Rolling開始時に、そのCFをPrepare済みの
設備容量・PV倍率・刻みへ変換する。日付・刻み・内容ハッシュが不一致なら実行を拒否する。

`src/optimization/rolling/pv_execution.py` は発行済みのバス充電量、BESS放電量、系統からBESSへの充電量を
維持し、現在枠の実測PVだけで供給元を決める。PVはBESS放電で残ったバス需要を優先し、次いで発行済み
PV→BESS指令の範囲まで充電し、余りを抑制する。PV不足時のバス需要は系統から補う。BESSを追加放電して
解を救済したり、バス充電量を後から減らしたりしない。実測PV不足でBESS充電が減った残量を次時刻へ引き継ぐ。

各枠で `SOC_next = SOC + eta_charge*(PV_to_BESS+grid_to_BESS) - BESS_to_bus/eta_discharge` とする。
SOC上下限・充放電電力・同時充放電禁止・充電時間帯／価格条件を検査する。系統上限がhardの設定なら超過は失敗。
既存設定がsoft契約超過課金なら、同じルールで超過kWhと費用を記録する。未確認の物理受電上限を捏造しない。
予測解は `hourly_solver_result.json`、実行した枠は `pv_execution.json` と `hourly_execution_result.json` へ分離する。
CLIにも `--pv-actuals-json` を追加し、BFFは別ソースの実測入力を同じCLI内部サービスへ渡す。

集計は実行した枠だけを一度ずつ連結する。予測期間全体の目的値を毎時加算しない。
実行後の各日末BESSも検査し、週末残量だけが戻っていても日次中立違反を受け入れない。
設備費は、充電ゼロの場合も宣言された設備の償却・維持費を対象日数分計上し、運転費と区別する。
供給元別のsolver出力行は物理充電指令へ合算した後に実行記録へ移す。車両別の供給元推定を
solver-nativeの厳密なprovenanceとして表示しない。日本時間の日境界を含む15件の制御・結合回帰を
通過したが、168時間の正式運行受入ではない。
