## 設定調整から基準解検証へ

実規模モデルは約679万変数・603万binaryで、threads削減でもroot中のメモリ停止が残る。
どの内部処理がピークを作るかは未特定。さらにPhase4は毎日の帰庫に未対応なので、
メモリを解消しただけでも週間総費用の統合最適性は証明できない。

`scripts/benchmarks/run_daily_assignment_reference.py` を追加した。
実時刻表の抜粋ではなく、明示した人工例（2日、1便/日、異なる電費のBEV2台、BESS、充電器1基）を使う。
全4割当それぞれについて既存daily-return固定Stage2・独立物理を検査する。
営業日内に1便しかないため、便の途中で車両を変更しないこの例の配車はこの4通りで尽くされる。
毎日の帰庫と翌日の出庫は既存物理タイムラインで別に扱う。

有効費用は車両日費100円と電力費。各割当の固定費C=200円、充電目的値qと下界lから、
総費用上界C+q、下界C+lを計算し、CostEvaluatorと1e−6円で照合する。
全割当の最小上界と最小下界が1e−6円以内で一致した場合だけ `NUMERICAL_REFERENCE_COMPLETE`。
OPTIMALというstatusだけに依存せず、gap0設定・native上下界・物理・配車不変・費用一致をすべて要求する。
[Gurobi MIPGap仕様](https://docs.gurobi.com/projects/optimizer/en/current/reference/parameters.html#mipgap)。
厳密算術の証明ではなく、保存した数値許容差の下での人工例の基準値である。

未解決・欠落・重複・割当差替え・非有限値・上下界逆転を成功扱いしない。
各時刻のPVだけを増やす例も全列挙し、最小総費用が増えないことを検査する。
Phase3候補費用が基準下界を下回らないことも確認する。新規7件を含む関連39 tests通過。
一般入力を受けるAPIは設けず、実規模への誤適用を防ぐ。
