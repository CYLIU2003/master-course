## 確認した停止要因

MATLAB_DESKTOPは搭載32GB、失敗開始時の空きRAM18.32GB。9/25の読取診断では物理空き約18.5GBに対しcommit limit127.68GiB、committed120.9GiBで追加確保余地は約6.8GiB。Windows System event2004が15:54:52に仮想メモリ不足を記録し、python PID13448が約8.52GBを確保していた。ジョブは15:55:09に失敗。現在のcommit値は失敗瞬間の計測ではないが、OSイベントとGurobi例外が整合する。commitの大量占有元は未確定であり、他アプリの無断終了やOS変更はしない。

親機の現在のcommit余地は約28GiB、他の32GB子機2台は約23GiB。単なる物理RAMキャッシュ解放はcommit不足の解決とは限らない。WindowsのGlobalMemoryStatusExのpage_total/page_availableはcommit容量（プロセス/Job制限を含み得る）であってpagefileの使用量ではない。[Microsoft仕様](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex)。

## 実装した対処

従来のresource_fitは物理RAMだけでMATLABを許可していた。commit計測を追加し、親機割当・投入直前・worker実行直前で不足/Windows計測不明を拒否。予約中の別attemptとOS予約分も割当時に控除し、不明な実行の枠は保持。32GB搭載制限、共有Gurobi枠、固定入力/物理条件は維持。これは事故予防であり全ケースの完走保証ではない。

先の修正で解消した別障害: 翌日帰庫回送の保存3分/復元8分不一致、診断Rollingの正式区分への暗黙変更、100窓以上の成果物辞書順。これらは過去のベンチマーク経路と新BFF/分散経路の差で、RAM増設では直らない。25便の7日実機テストで修正後の通過を確認済み。

次の実験は現有DESKTOP-6AE0MIRの32GB機で2月1週を新規Prepareから実行。共有枠は維持し、他11週は停止継続。新コードの完走・費用検算が出るまで解決済みと宣言しない。既存12週の進捗資料と数値はそのSHA/条件の証拠として保持する。
