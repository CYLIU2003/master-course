# 4月の週末BESS復元不能による停止

固定 `2ff239e1dc488409e8cf215bff918953fd36346f` の月別実行は、1〜3月の3週で独立監査を通過し、4月7日開始週のhour 158で停止した。158/168時間まで受理、5〜12月は未実行。4月の週間物理検証・確定週間会計は成立していない。監視は計算停止を正しく検出し、2026-09-19 20:14 JSTに一度だけ既存タスクへ通知した。完了メールは送信していない。

## 確認できた原因

4月13日14時の残り10時間について、保存IISには以下が同時に含まれる。

- 初期BESS残量: 2,143.238688133444 kWh。
- 残り40 slotの予測PV合計: 844.579 kWh。
- 系統電力からBESSへの充電: 全40 slotで禁止。
- BESS充電効率: 0.95。
- 週末残量の等式: 3,000 kWh。

残りのPVを全部BESSへ充電し、バスへのPV供給とBESS放電をゼロとする楽観的な上界でも、

`E_end <= 2143.238688133444 + 0.95 × 844.579 = 2945.588738133444 kWh`

となる。目標との差は **54.411261866556 kWh**。電力・充放電モード等を無視した上界さえ目標に届かないため、この開始状態と予測・供給源条件では時間延長や探索設定変更で解消しない。54.4 kWhは上記の楽観条件での不足下限であり、実行可能な補給計画や必要設備容量の算定値ではない。

直前のhour 157（13〜14時、slot 628〜631）のPVは予測464.828 kWhに対し、履歴による実績再生値68.0 kWhだった。バスへの直接供給7.5 kWhを差し引き、BESS充電は60.5 kWh。14時のBESSは予測2,520.225288133443 kWhに対し実績再生2,143.238688133444 kWhで、376.9866 kWhの差が生じた。保存済み各slotのエネルギー式と次時刻への引継ぎは整合しており、残量の単純な転記誤りではない。

ここでの「実績」はSolcast履歴から作った再生入力であり、営業所の実測発電量を意味しない。残りの実績PVを先読みして原因判定や計画に使っていない。

## 実装経路と不足していた保証

`run_shibu21_seasonal_diagnostic.solve_week` → `RollingReoptimizer.reoptimize_charging_hour` → Stage 2の予測計画 → `execute_pv_prefix` → `build_next_execution_state` → 次のhourという経路を確認した。PVが不足したとき、実行器は指令済みのバス充電・BESS放電を維持し、観測PVに応じて実際のPV充電量を減らす。BESSへの系統充電を後から追加する仕組みではない。

`src/optimization/milp/pv_execution_reserve.py` の既存制約は、直近1時間のPVがゼロでも物理下限1,200 kWhを割らないための予備残量を確保する。一方、週末3,000 kWhへの到達可能性は予測計画上の判定であり、予測誤差を受けた後も到達可能である保証はなかった。新しい週末復元条件を加えただけでは、この保証の不足は埋まらない。
