# 計算用PCを研究室の後輩にも使えるようにする方針案

2026-11-19。案の整理であり、実装・設定変更・ライセンス操作は行っていない。
根拠は既存文書（[分散計算](../DISTRIBUTED_COMPUTE.md)、[研究室の計算依頼](../guides/lab_compute_intake.md)、
[Gurobiライセンス記録](GUROBI_LICENSE_DEPLOYMENT_20261010.md)、[Gurobi 32GB制限](GUROBI_ADMISSION_POLICY_20260925.md)）と
`config/cluster/workers.local.json`（17件）の読取り。

## 1. 今あるもの（確認済み）

- 親機1台が計算を割り振り、子機（worker）へSSH（Tailscale経由）で投入する。台帳に17件。
  うち `enabled` かつ `gurobi` が有効なのは13件、新規導入のうち4件は割当停止で登録（11/07にDESKTOP-GSFGTJ2のみ有効化）。
- 受付画面（「研究室の計算依頼」）は親機のloopbackのみ。後輩が直接使える入口はない。
  運用は「後輩が依頼テンプレートを渡す → 親機の利用者が登録 → `REVIEW_REQUIRED` で止まる → 確認後に投入」。
- 受付簿をジョブへ自動連結する機能、複数利用者向けの認証・遠隔ポータル、任意プログラムの実行サービスは未実装。
- 同時に走れるGurobiは共有2枠、かつ搭載RAM32GB以上の端末のみ。台数が多くても同時実行は2件が上限。
- 各端末のGurobiは「ユーザー個人のNamed-User（Free Academic）」として導入したもの。
  EULAにNamed Userの共有・バッチ・常駐サービス利用の制限があり、後輩への流用や同時実行の増加とは扱っていない。

## 2. 後輩に使わせるうえでの制約

1. **ライセンス**：個人用Named-Userや親機の資格情報を後輩に複製・自動適用しない。台数ではなく枠（2）とライセンス条件が実質の上限。
2. **台の所有**：台帳の端末には研究室の共用機と思われるもの（POWERSYSTEM、PSLAB系、MATLAB_DESKTOPなど）がある。
   私物か共用か、使わせてよい範囲を台ごとに確認する必要がある（記録上は「全部私の端末」とされた時期があるが、現在の所有・管理者は未確認）。
3. **安全**：後輩をTailnetや子機のSSH鍵に加えない。親機の管理画面を他者に開放しない（認証が未実装）。
4. **再現性**：研究用の固定版・Prepare済み入力・SHAの規則があるため、後輩の計算はこの修論モデルの正式運用と混ぜない。

## 3. 実現形（案）

| 案 | 内容 | 追加実装 | ライセンス | 向く場面 |
|---|---|---|---|---|
| A. 受付簿運用（現状の延長） | 後輩はテンプレートで依頼、親機の利用者が登録・確認・投入。結果はファイルで返す | なし | 親機側の枠2を時間で分け合う | 当面。依頼が週数件まで |
| B. 時間貸し（予約表） | 枠2の使用時間帯を後輩ごとに割り当て、計算は後輩自身がその時間に自分の依頼を実行（親機の操作は依頼者側で） | 予約表の運用のみ | 同上。個人資格情報は渡さない | 複数人が同時期に使うとき |
| C. 後輩ごとのライセンス | 各自が自分の学術ライセンスを取得し、台に各自の環境で導入。台は「計算機」として貸す | worker側のユーザー分離、配置手順 | 各自（EULA上の利用者は本人） | 後輩が自分でGurobiを回したい |
| D. 認証付きの共用ポータル | 複数利用者の認証、依頼から投入までの自動化、利用者別の枠管理 | 大（認証・権限・監査・ジョブ連結・任意コードの隔離） | 方式の再確認が必要 | 利用が常時・多人数になった場合のみ |
| E. 非Gurobiソルバー限定の開放 | HiGHS等のOSSを使う後輩には、ライセンス枠と無関係に台を開放 | 別ランナーの実装・検証 | 不要 | 後輩の問題が小さい／OSSで足りる |

推奨は **A → B**（まず現状で受ける、混み始めたら予約表）。Gurobiを自分で使いたい後輩が出たら **C**、
それでも足りなくなった時点で **D** を検討する。Dは今の人数では過剰で、認証と任意コード隔離の設計が前提になる。

## 4. 決めてほしいこと

1. 対象の後輩の人数と、計算の内容（この修論モデルのシナリオ／別のPythonコード／Gurobiの有無）。
2. 台ごとの所有と、使わせてよい範囲（研究室の共用機か私物か、管理者・指導教員の了承）。
3. Gurobiについて、後輩の利用を研究室のライセンス方針（教員への確認を含む）に合わせるか、各自取得にするか。
4. 受付を親機の利用者が代行する運用で当面よいか、後輩が自分で依頼できる入口がどうしても必要か。

## 5. 最初にやること（案Aの準備、設定変更を伴わない）

- [研究室の計算依頼](../guides/lab_compute_intake.md)のテンプレートを後輩向けに1枚にまとめて渡す。
- 台の所有・使用可否の一覧（台ごと）を作り、後輩に開放する台と、研究専用に残す台を分ける。
- 優先順位の規則（修論の正式運用を優先、後輩の依頼は空きの枠で実行）を決めて共有する。

## 6. 後輩のAIが直接タスクを投入する形（2026-11-19追記・方針変更）

条件は「4人程度、全員Gurobi、空いている台は使ってよい、劉の計算が最優先、ライセンスは各台に用意されたもの」。
後輩のAIが親機へ直接タスクを投入する形にする。指示書は [junior_ai_instructions.md](../guides/junior_ai_instructions.md)。
案Dに相当し、現状の実装では**そのままでは実現できない**。必要なもの（いずれも未実装、または未確認）:

1. **受付ゲートウェイ**：後輩のPCから届く、認証付きの入口。現在の `/api/cluster`（`POST /jobs`、`GET /jobs/{id}`、
   `POST /jobs/{id}/cancel`、`GET /jobs/{id}/artifacts`）は loopback と Host/Origin に限定され、複数利用者の認証がない。
   後輩にはこれらのうち投入・自分のタスクの状態・自分のタスクの取り消し・成果物のみを、利用者ごとの認証で許す。
   子機・SSH鍵・親機の管理画面・他人のタスクは見せない。
2. **到達経路**：後輩のPCから親機のゲートウェイへつなぐ方法（Tailscaleの共有や通信制限など）。
   これはネットワーク・セキュリティ設定の変更に当たり、運用者が行う。台や子機のSSHへは到達させない。
3. **優先度と割込み**：スケジューラに優先度は見つけられなかった（`src`・`tools` の検索の範囲）。
   劉のタスクが後輩のタスクを止めて割り込む仕組み（低優先の印、割当時の優先、停止要求の自動化）が要る。
4. **実行できる内容**：現在のクラスタは、凍結済みの入力（Prepared）から修論モデルを解くことと診断が対象で、
   任意のコマンド・スクリプトの実行は行わない。後輩が自分のPythonコードで書いたGurobiの問題は、そのままでは動かせない。
   動かすには、利用者ごとの隔離、依存環境、入力・成果物の検査を備えた別の実行器が要る。
5. **同時枠**：後輩が増えても、同時に走るGurobiは共有枠の2件まで（`global_gurobi_slots`）。
   各台のライセンスを使ってよいことと、この枠を増やすことは別の判断。Named-UserのEULA（共有・バッチ・常駐利用の制限）の確認が残る。
6. **台の開放範囲**：研究室の共用機と思われる台の所有者・指導教員の了承を、台ごとに確認する。

2〜4が整うまで、指示書は配布しても有効にならない。当面は案A（劉が依頼を代行登録）で運用する。

## 7. メモリ上限が低い台の扱い（2026-11-19追記）

方針：メモリが小さい台も、後輩向けなら使う（劉の指示）。修論の研究計算には従来の「搭載32GB以上」を維持する。

- 既存の32GB条件（[GUROBI_ADMISSION_POLICY_20260925.md](GUROBI_ADMISSION_POLICY_20260925.md)）は、配置・起動直前・worker実行直前の検査としてコードに入っており、
  設定では迂回できない。後輩向けに低RAM台を使うには、台ごと（または用途ごと）にこの検査を切り替える実装変更と回帰テストが要る。
  この変更は未実施。実施するときは、修論の研究計算が低RAM台へ割り当てられないことを先にテストで固定する。
- 台帳に低RAMの台がある（例：DESKTOP-MR7177O 15.9 GiB。ほかのRAMは未確認）。タスク側の「必要メモリ」と台のRAMの照合は、割当前に行う。
- 低RAMの台は、重いタスクで落ちやすい。落ちた結果は自動再試行せず、依頼者へ返す。

## 8. 訂正と現状の確認（2026-11-19追記）

- 上の1・2・5・7節にある「搭載32GB以上」は古い記録（2026-09-25）に基づく。コードの現在値は**24GB**
  （`bff/services/cluster/resource_policy.py` の `GUROBI_MINIMUM_INSTALLED_RAM_GB`、2026-11-07のユーザー決定）。
  24GB未満でGurobiが拒否される点は変わらない。台帳でこれに当たるのは desktop-mr7177o（15.9 GiB）と、記録上 cyliu-thinkbook（23.8 GiB）。
  31.7〜31.8 GiBの台（baia67v、pslab-mouse）は条件を満たす。
- タスクごとのメモリ上限（搭載−8 GiB、半分を下回らない）、空きRAM、Windowsのコミット余裕の検査は別に働き、低RAM台では大きなタスクが自動的に弾かれる。
- 親機の台帳 `config/cluster/workers.local.json` は `global_gurobi_slots=2`・`external_gurobi_slots=1`。スケジューラ（`scheduler.py` の `tick`）は
  この上限で同時Gurobi数を止める。「台ごとのライセンスで置き換わった」というコード内のコメントとは、実際の挙動が異なる。
- 24GB未満の台でGurobiを許可するには、親機側（`resource_policy.py`、`scheduler.py`、`worker_registry.py`）に加えて、
  子機側で動く `runner.py` と `solver_policy.py` も変える必要がある。子機側は各台の固定版の中にあるため、変更後は全台へ再配置（stage）が要る。

## 9. 台の優先順位の方針と、稼働中の構成の訂正（2026-11-19追記）

**方針（劉の指示）**：修論で使っていない台を、後輩が優先して使う。それでも足りないときは、優先ではない形で修論用の台も使ってよい
（修論の計算が来たら後輩のタスクを譲る）。低RAMの台も後輩向けには使う。ライセンスは各台に用意されたもの。

**訂正**：8節の「同時枠は2」は親機の台帳 `config/cluster/workers.local.json`（現在使っていない旧い版）の値だった。
稼働中の8891の最新設定 `output/midterm_20261128/workers.deployed.v62.json` は `global_gurobi_slots=14`・`external_gurobi_slots=0`、
12台が有効（local、matlab-desktop、desktop-3pru7qp（3枠）、desktop-5b6f6bp、desktop-6ae0mir、laptop-a709una0、pslab-mouse、
desktop-baia67v、desktop-1800n4s、desktop-mr7177o、hp-desktop-2、desktop-gsfgtj2（2枠））。これが現在の修論用の台。
台帳にあって修論用でない台（候補）：desktop-0srs8pr、powersystem、cyliu-thinkbook（オンライン）、cyliu-dell-7260、pslab-e490、laptopintel8、
laptop-fem8jhv2、laptop-d0stmfn4（オフライン、11/19時点のTailscale）。

**実現に必要なもの**（未実装。後輩のタスクを区別する印と受付口が先に要る）：
1. 台の区分：`修論用` と `後輩優先` の2種（台帳の台ごとの項目）。
2. 後輩のタスクの印（受付口が付ける。後輩は印を外せない）。
3. 割当の並べ替え：後輩のタスクは `後輩優先` の台を先に、足りなければ `修論用` の台。修論のタスクは `修論用` だけ。
4. 割込み：修論のタスクが入ったとき、`修論用` の台で動く後輩のタスクを停止要求（既存のattempt単位の停止）して台を空ける。
5. 後輩のタスクは再開できないので、中断を前提に時間上限を短く切る（指示書に記載済み）。

**実装済み（ブランチ `feat/lab-low-ram-gurobi`、コミット bb93ff51、mainには未統合）**：台ごとのGurobi搭載RAM下限。
詳細は同ブランチの `DEVELOPMENT_NOTES.md`。固定版（11/28用）には入っていない。統合と全台への再配置は、中間発表後にするか判断が要る。

## 10. 実装状況（2026-11-19 夜、ブランチ `feat/lab-gateway`）

案D相当の受付口（ラボゲートウェイ）を、修論用のクラスタとは別のサービスとして実装し、実機で確認した。使い方・運用手順・検証範囲は
[lab_gateway.md](../guides/lab_gateway.md)、後輩のAI向けの指示書は [junior_ai_instructions.md](../guides/junior_ai_instructions.md)。

- 実現した方針：後輩のAIが認証つきの受付口へ直接タスクを投入する。台は修論用でない3台（cyliu-thinkbook、powersystem、desktop-0srs8pr）。
  低RAMの台も、台ごとの空きRAMと上限（搭載−8 GiB）の検査だけで使える。そのため 8節の台ごとのGurobi下限（`feat/lab-low-ram-gurobi`）は、この経路には不要。
- 後輩のコードの実行：台のPython環境で `python <entry>` のみ。zipの経路・サイズ・シンボリックリンクを検査し、シェルは使わない。台のログインユーザーの権限と
  そのユーザーのGurobiライセンスで動く（運用者了承）。
- **未実装**：修論用の台への「優先でない」あふれ出しと、修論の計算が来たときの割込み。8891の制御系と台を共有する連携が要るので、中間発表（11/28）後に設計する。
- **運用者の作業が残る**：後輩のPCから親機への経路（ファイアウォール、Tailscale共有など）、人ごとのトークンの発行と個別の受け渡し、起動。
